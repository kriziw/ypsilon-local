# Runxin F79D profile

The F79D profile is the device knowledge currently used by Ypsilon. Field ids, read codecs and known write encodings live in `runxin/fields.py`; `runxin/f79d.py` turns that catalogue into frames and decoded state.

For the evidence trail behind the legacy WaterDevice application, real-device observations and safety decisions, also see [`waterdevice-audit.md`](waterdevice-audit.md). Recovered advanced-setting enum maps, numeric ranges and their Home Assistant surface are documented in [`f79d-settings.md`](f79d-settings.md) ([ES](f79d-settings.es.md), [CA](f79d-settings.ca.md)).

## Evidence legend

- **A** — present in the legacy WaterDevice field/codec implementation;
- **O** — value/behavior observed on the project's real Ypsilon/F79D data;
- **HW** — local write exercised end-to-end against the physical controller and confirmed through an independent fresh local read-back;
- **CW** — value change observed through the vendor/cloud application path.

`A` documents how the recovered application codec represents a field. It does **not** override contradictory physical-controller evidence. A transport ACK without matching fresh read-back is not `HW` evidence. Field 7 deliberately omits `A` from its encoding evidence because the recovered application interpretation conflicts with the tested G6 wire/read-back behavior.

## Field catalogue

The catalogue's hardware-write evidence refers to the reference Ypsilon G6. Model 12 reuses the observed framing/map under experimental / Alpha support, with its own verified/pending field lists in `models.py` and [hardware verification](hardware-verification.md#euro-clear-midnight--controller-model-12). Model 14 has Beta support with a field-26 U16 LE override: `[44, 1]` → 300 → 30.0 L, confirmed by its controller photo. ## Home Assistant surface for recovered advanced settings

Fields 2, 3, 24 and 48 are genuine WaterDevice enums and are therefore exposed as Home Assistant enum sensors rather than raw integer sensors. They are diagnostics disabled by default, preserve stable untranslated state keys, and retain the controller code in `raw_code`.

Fields 13, 14 and 25 are numeric settings, not enums. Fields 13 and 14 remain disabled-by-default read-only diagnostics. Field 25 is enabled by default because it is the controller's native regeneration-count threshold for the resin-maintenance reminder and is useful to derived Home Assistant maintenance logic. It must not be confused with a current or lifetime regeneration counter.

## Field 7 hardware endianness correction in 2.6.3

The recovered WaterDevice path appeared to serialise field 7 with a generic little-endian helper. Physical controller evidence proves that interpretation is not correct for the tested Ypsilon G6:

```text
wire bytes: 03 E8
BE: 0x03E8 = 1000 -> 10.00 m³/h
LE: 0xE803 = 59395 -> 593.95 m³/h
```

The vendor application displayed 10.00 m³/h while Ypsilon 2.6.2, using the LE regression, displayed 593.95 m³/h. This independently proves that the tested controller's field-7 wire representation is big-endian.

The write path corroborates the same conclusion. A requested 2.00 m³/h is raw 200 (`0x00C8`) and must be sent as `00 C8`. The LE regression sent `C8 00`; the transport/protocol layer ACKed the request, but repeated fresh reads retained the previous physical value and the integration correctly raised `Write ACKed but not confirmed`.

Earlier Ypsilon versions using BE had already completed successful end-to-end physical SET/read-back validation for field 7. Version 2.6.3 therefore restores BE read/write and `HARDWARE_WRITE_VERIFIED`. The legacy-app discrepancy remains documented for interoperability research rather than being hidden.

## Unit-dependent volume-pair reconstruction

Fields 35, 37, 39 and 41 consume the immediately following continuation field. Let the relevant bytes be:

```text
base field:          [id, base_low, base_high]
continuation field:  [id+1, next_low, next_high]
```

The legacy application constructs the logical three-byte value as:

```text
[next_high, next_low, base_high]
```

and then interprets it according to `waterVolumeUnit`:

- unit `0` or `1`: 24-bit little-endian integer
  `next_high + (next_low << 8) + (base_high << 16)`;
- unit `2`: decimal/base-100 packing
  `next_high + next_low*100 + base_high*10000`, presented by Ypsilon in cubic metres with `/100` scaling.

If the unit field or continuation field is missing, Ypsilon returns `None` rather than fabricating a plausible zero.

## Water/statistics semantics validated for 2.6.1

### Daily consumption — fields 37–38

A real exported history from the tested G6 shows the field rising during each day and resetting near the day boundary. In Home Assistant this is therefore exposed as `TOTAL_INCREASING`: a reset starts a new meter cycle and is not interpreted as negative consumption.

### Controller weekly average — fields 39–40

The live controller value and the vendor application's week-by-week history bars are different quantities. The application has a separate statistics path for the historical weekly bars. Field 39 is therefore named **Controller weekly average consumption** and intentionally has no Home Assistant `state_class`.

### Treatment capacity per cycle — fields 41–42

The legacy UI treats this as a treatment/cycle capacity/configuration quantity. It is not a cumulative water meter, so it intentionally has no `state_class`.

Older integration versions briefly generated long-term statistics for fields 39 and 41. Home Assistant may offer to delete those obsolete statistics after upgrade; that cleanup does not remove the entities or their normal recorder history.

## Flow units and field-7 limits

The legacy UI labels field 11 as:

- unit 0: `gpm`;
- unit 1: `Lpm` (`L/min`);
- unit 2: `m³/h`.

Only unit 2 has been calibrated end-to-end on the project's physical Ypsilon G6. The field-7 Home Assistant control therefore remains available only in unit code 2. For this unit family the controller/vendor UI limits field 7 to 10.00 m³/h, matching raw hundredths 0–1000. Field 6 is similarly constrained to the WaterDevice 0–120 minute range.

## Salt semantics

Field 43 is the legacy `addSalt` setting. The vendor UI presents it as a 0–100 kg **amount of salt added**. Local SET/read-back has been physically verified and the same value has also been observed changing through the vendor path.

It is not a physical level sensor. Ypsilon therefore does not decrement it after regeneration and does not treat it as salt remaining. Low-brine and add-salt/reminder conditions are provided by separate controller fields 31 and 33.

## Vacation semantics and the 2.6.1 safety decision

The recovered legacy UI models vacation mode using field 49 and only enters from `systemMode == 0`; it leaves from stable `systemMode == 8`. It also reveals the legacy progression `0 -> 3 -> 7 -> 2 -> 8` and uses 25% of the normal slow-wash duration for the vacation brine-draw progress display.

However, that is application/codec evidence, not current-firmware hardware evidence. On the project's physical G6, v2.6.0 sent a direct local field-49 write, received a transport/protocol ACK, then repeatedly performed fresh reads. `vacationPattern` remained `false` until timeout.

Consequently v2.6.1:

- continues reading field 49;
- keeps field-49 encoding in the reusable F79D codec for interoperability research;
- does **not** mark field 49 `HARDWARE_WRITE_VERIFIED`;
- removes the writable Home Assistant Vacation mode switch;
- retains the read-only semantic Vacation status sensor;
- sends no guessed multi-field/mechanical sequence.

Read-only semantic state remains:

- `off`: field 49 false;
- `preparing`: field 49 true, station not 8;
- `active`: field 49 true, station 8.

Stable `vacation + station 8` is not considered mechanical activity for adaptive polling. Transition phases remain active-poll states.

## Safe Home Assistant write surface

The protocol codec knows how to serialise more fields than Home Assistant exposes. The generic administrator `write_fields` service is deliberately limited to reversible configuration fields and applies range/unit validation. Fields 34 and 49 are excluded from that generic service. Field 49 has no purpose-specific HA writer because its local action is not physically verified on the tested current controller.

## Field 52 polling

The normal state query remains fields 1..51. Field 52 is read separately and cached by the Ypsilon integration. That is an integration polling policy, not part of the generic Runxin transport contract.
